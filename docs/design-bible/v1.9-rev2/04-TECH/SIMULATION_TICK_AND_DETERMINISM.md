# 仿真、固定 Tick、因果、跨区与事件契约

## 总体不变量 [BASELINE]

`WorldState --(visibility)--> Observation --(controller)--> Intent[] --(validation/resolve)--> NewWorldState + Events --(presentation)--> UI`

相同的**游戏版本、平台构建、初始存档、种子、输入与控制器版本**，应得到一致的游戏状态序列和事件序列。[BASELINE] 初期先保证相同平台/同构建的确定性，不假装已经完成跨平台浮点确定性。

## Tick 频率

此前以 **20 Tick/s** 作为技术实验候选，但**尚未冻结**。需依据战斗手感、网络延迟、500+ 实体负载、离屏区更新和主线程预算实测。画面渲染 FPS 可高于仿真 Tick，通过插值显示。

## 候选 Tick 管线 [PROPOSED]

1. 处理上个 Tick 已承诺、此时应到达的消息与事件。
2. 使用当前真状态生成玩家/对手/设备的合法 Observation。
3. 执行预算内 JS/策略，生成序列化 Intent；故障控制器提供结构化退化事件。
4. 按稳定调度顺序验证意图（资源、模块、已知目标、距离、权限、区域）。
5. 计算供能/生产/物流、移动/攻击/护盾等结果，保证守恒。
6. 将新消息加入未来交付队列，不能当 Tick 即刻穿越链路。
7. 更新文明状态和世界事件，提交一致快照与可视事件。
8. 生成状态摘要/可复现回放记录。

**注意**：时序的每一个冲突点必须形成具体测试。上面并非最终事件先后标准。

## 多区域与同步

- 每个区域是真实 2D 场地；跨区链接代表显式运输/数据/供能能力。
- 同一世界内不同区域推进不能互相“跳过”已产生的事件。离屏区域可采用精度简化，但结算必须可验证。
- 远端通信与物流需队列和延迟，事件可跨区引用稳定 ID。
- 区域加载/卸载不能随机改变产出量、事件顺序或库存。
- 可配置模拟策略不应成为玩家利用“视角切换”刷资源/重置敌人的入口。

## 战斗与显示分离

命中、损伤、能耗、护盾、模块失效必须是仿真事件产生的事实。Godot 只依据事件播放射击、粒子、护盾受击、断线和 UI 更新，不允许 Shader 决定伤害。

## 脚本与信息因果

- Observation 只能包含合法传感器发现、己方已知信息和成功收到的消息。
- 程序没有权限从全世界列表筛选隐藏敌人。
- 消息具备 `sentTick`、`deliverTick`、链路/带宽/目标验证；本 Tick 发出消息不会本 Tick 到达远端。
- 通信中断应使远端继续使用本地已知状态，但不得神奇读取更新。

## 建议的错误事件 [PROPOSED]

`NO_ENERGY / NO_MATERIAL / OUT_OF_RANGE / TARGET_UNKNOWN / NO_LINE_OF_SIGHT / MODULE_DISABLED / NO_ROUTE / NO_BANDWIDTH / COMPUTE_BUDGET_EXCEEDED / SCRIPT_TIMEOUT / SCRIPT_FAULT / INVALID_ACTION / DEPLOYMENT_REJECTED`。

错误码应稳定版本化，UI 用人类可读语句和诊断上下文解释。不同错误不可全变成无反馈的 `wait`。

## 自动化验收

- 固定种子连续 N=5,000 Tick 的状态摘要重复性（N 为回归用例，非产品容量承诺）。
- 消息至少后续 Tick 到达；断联不可读取新敌情。
- 同资源下发射/移动/生产守恒，不能在同 Tick 双重消费同一库存。
- Headless 与带画面模式输出相同仿真状态。
- 跨区加载顺序与区域间迁移不改变随机事件因果。
- 脚本超限和异常不能破坏世界提交事务；意图被统一拒绝或安全回退。
