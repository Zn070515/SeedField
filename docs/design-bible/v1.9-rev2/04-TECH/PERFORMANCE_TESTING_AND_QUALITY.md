# 性能、测试矩阵与产品质量

## 性能优先问题

大规模自治 JS 控制器、跨区世界演化、通信网络、资源/物流结算、实体空间搜索、战斗弹体、Godot 2D 绘制、Jint 内存和垃圾回收是主要成本。必须测真实工作负载，不能简单假设高端开发机跑得动就代表正式版可发行。

## 测试层次

| 层次 | 必须覆盖 | 主要证据 |
|---|---|---|
| Schema/规则单元测试 | 资源守恒、消息时序、预算、权限、版本化 | 断言、运行日志 |
| Headless 仿真测试 | 固定种子/状态/输入多次运行相同 | 状态/事件摘要 |
| 安全/故障注入 | 死循环、超限、恶意数据、I/O 越权、进程故障 | 失败恢复与受阻证据 |
| 大规模性能 | 多脚本、密集单位、多区、渲染压力 | P50/P95/P99 与内存曲线 |
| 视觉集成 | 实际 Godot 机体、网络、能量、发射和受击 | 真实运行截图/视频 |
| 交互可玩性 | 五分支教程、首战、调试、复建、构造进阶 | 真实玩家试玩记录 |
| 完整产品回归 | 存档迁移、导入包、文明/终局、断网 | 端到端验收 |

## 基础规则回归

1. 不可知目标：断开感知/通信后，设备不能获得未观察到的敌人当前位置。
2. 不可超前消息：Tick T 的消息不能在同一 Tick 被收件方使用。
3. 资源守恒：移动/攻击/防护/生产的费用和跨区库存一致。
4. 算力与权限：相同硬件不同 JS 行为产生差异；非法 API 被拒。
5. 执行稳健：无限循环、巨大内存、异常程序不能导致世界错误提交。
6. 核心区恢复：所有外部资产为零仍可由保底再生恢复最低行动设备。
7. 布局/程序版本：工坊更新不会瞬间改变世界旧实例。
8. 区域连接：跨区信息/物资/实体没有免费瞬移和状态丢失。
9. 内置对手：与玩家同一物理/信息/资源结算约束。
10. 终局后延续：触发终局变化后继续建造、编程、探索和存档。

## 固定 Tick与 FPS 目标

`20 Tick/s` 是此前提出的**候选**，非已批准最终值。目标 FPS、最低 Windows 配置、最大实体/区域/控制器数均要经实际基准和目标市场评价后确定。不可虚构 1000 控制器稳态 60 FPS 等量化承诺。

## 安全不仅是测试绿

Jint 属嵌入式进程内解释器；对非可信文明包要在 OS 级隔离与 IPC 校验通过后才开放运行。若游戏首发时安全方案尚未完成，可以先内置合法对手，延后可执行外部包导入，**但需如实披露不能宣称已支持任意社区 JS**。

## 真人试玩重点

- 非程序员是否能完成最低五分支、进入 PvE。
- 30–60 分钟首次正式攻防目标是否可达到，是否被长教程拖慢。
- JS 程序修改与战局变化之间是否可感知、可解释。
- 断供/失联失败是否变成挫败而不是系统谜题。
- 自由目标与文明事件是否帮助探索而非隐藏强制任务。
- 核心区毁灭恢复是否避免完全挫败，同时保留战争损失压力。

## Go/No-Go 决策原则

技术/玩法/艺术的重大风险必须在小规模试验里被验证：例如脚本性能不达标时优先优化或评估执行模型；安全隔离做不到时不开放未知代码；艺术路线成本过高时减少模块数量而不是放弃视觉品质；如果用户无意修改程序，则反思教程/可解释反馈而不是一味加数值奖励。
