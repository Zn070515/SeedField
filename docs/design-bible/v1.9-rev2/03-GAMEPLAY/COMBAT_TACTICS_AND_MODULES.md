# 战斗、模块化战构体与策略

## 战斗的定位 [BASELINE]

战斗是检验玩家工业体系、通信网络、控制程序、侦察能力和资源分配的实际场景，而不是以手动微操为主的独立竞技游戏。玩家可实时设定任务和暂停调整，但局部移动/感知/目标选择/攻击依自主程序执行。

## 典型交战链路

`侦察获取有限目标信息 → 通过通信链路传输情报 → 控制器根据本地状态/协议分配任务 → 战构体执行移动、火力、护盾等意图 → 仿真核结算能源、模块能力、命中、损伤 → 反馈与修复/撤退/再部署`。

任一环节都可能成为策略瓶颈：失联、误判、供电不足、处理器预算超额、仓库缺料、部署版本旧、传感器范围不足。

## 模块化设备的关键取舍

- **机架**：体型、负载、安装位、机动与可视轮廓。
- **驱动**：移动能力与能源/质量代价。
- **传感器**：侦察类型、范围、精度与功耗。
- **通信**：中继/收发、带宽与断联鲁棒性。
- **处理/状态**：算力、存储、控制器程序容量。
- **武器/护盾**：射程、能耗、冷却、命中/拦截能力。
- **维修/后勤**：恢复与继续作战能力（具体首发范围待定）。

这些不是已经冻结的完整元件清单，具体平衡由原型与试玩决定。[PROPOSED/VALIDATE]

## 最低战斗闭环 [PROPOSED 示例]

一片二维小区域，至少两台拥有能源和局部传感器的玩家设备、一台使用同一接口的离线对手、一个需要守住或夺取的通信节点。设备根据 JS 控制程序移动、开火、护盾受击；渲染只表现 `Events`，不改变命中结果。

## 规则不变量

- 武器/护盾/移动/模块失效都交给 SimulationCore 结算，粒子/音效没有权力决定胜负。
- 对手无法凭空知道尚未感知的目标位置、绕开能源短缺或移动到禁止区域。
- 失联设备仍可通过本地程序自治，而不是立刻全图停机。
- 在相同硬件和资源下，不同玩家程序能产生可观察的战术差异。
- 击毁、缴获、维修与再生产的原料成本不能破坏资源守恒。

## 大型后期武器方向 [历史保留，不是首发承诺]

讨论中出现过「贯星长枪」「蜂群织刃」「断链风暴」「天幕裁决」等概念性特色系统。保留为远期构想，尚未冻结真实机制、材料成本和内容规模。不得在 M0 或首个可玩版中为这些名称建立庞大空架构。

## 战役胜利与整体存续

战斗可以由占领节点、保持控制时长、迫退敌方、摧毁工业链/军事设施、守住补给线等条件判定。[PROPOSED]

**玩家不可摧毁的核心区不能被胜利条件偷换为可攻击的基地核心。** 对手离线文明的核心是否也具备永久保护属于开放问题。正式游戏应保证外部损失真实、战争有明确结算，但不制造玩家永远无法复建的围困死局。

## 可理解性要求

战斗结束至少能解释：目标为何可见/不可见、决定为何产生、命令为何失败、能耗发生在哪里、命中与护盾如何结算、哪一处通信/能源链路导致战术崩溃。
