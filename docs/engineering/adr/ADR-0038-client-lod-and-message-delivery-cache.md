# ADR-0038：客户端人群 LOD 与消息投递批缓存

- 状态：**Accepted**
- 日期：2026-11-17
- 关联：ADR-0037（观测消息上限）、ADR-0033（离屏）、Issue #19
- 触发：混合客户端基准中 1000 台 Tick 仍约 29 ms、渲染约 28 FPS

## 背景

ADR-0037 把观测消息限制为最近 32 条后，1000 台真实 scout 从 309 ms/Tick
降到约 28 ms/Tick。继续分段测量发现：

- 观测 4.27 ms、决策 4.22 ms、结算 **20.01 ms**、呈现 0.75 ms；
- 结算的瓶颈是 `DeliverDueMessages` 对**每条消息**调用
  `GetMessageStorage`，而后者遍历整个世界实体；
- 1000 条本地消息 × 1000 个实体 → 每 Tick 约 10^6 次字符串比较/扫描；
- 渲染仍按每个实体绘制阴影、尘土、血条/能量条，1000 台约 4600 draw calls，
  在 1280×720 下约 25 ms。

## 决定

### 1. 消息投递批缓存

`DeliverDueMessages` 在每批投递内按文明缓存
`(HasStorage, Capacity)`，同一文明只扫描一次实体。收件箱容量/过期语义、
消息顺序、事件、存档与哈希不变。

### 2. 人群/远景 LOD

当可见实体数 ≥ 400 或缩放 < 0.9 时：

- 每个实体只画一个带朝向的纹理四边形；
- 跳过阴影、移动尘土、血条/能量条、ID/调试标签；
- 视口外实体直接裁剪；
- `_debugVisible` 时仍走完整绘制，截图/调试不受影响；
- 低于阈值（正常小队）保持完整表现。

### 3. 范围

只改呈现层与消息投递内部缓存；不改仿真规则、世界状态、存档、哈希、
网络带宽或 Intent 顺序。

## 非目标

- 不引入 MultiMesh/纹理图集或替换渲染器。
- 不对核心、网络、控制点、UI 做 LOD。
- 不改变 400 阈值/0.9 缩放为场景配置（后续可评估）。
- 不改变收件箱存储容量与脚本消息历史（ADR-0037 已定义 32 条窗口）。

## 后果

- 1000 台真实 scout 混合负载：约 **10.2 ms/Tick、p95 12.1 ms、~372 FPS**
  （1280×720，vsync off）；500 台约 4.8 ms/Tick、505 FPS；100 台约 1.4 ms、
  159 FPS（仍完整绘制）。
- 1000 台 Draw Calls 从约 4600 降到约 720（保留 8 方向纹理）。
- 峰值内存约 577 MiB；GC 暂停仍在（约 101 ms/2 s），后续可继续优化分配。
- 人群 LOD 隐藏单体血条/尘土；这是明确的呈现取舍，调试/近景仍完整。

## 验证

- 分段计时：`obsMs/decideMs/stepMs/presentMs` 输出在 `MIXED_BENCH`。
- 1000 台：step 20.01 → 2.02 ms；总 29.26 → 10.24 ms。
- 消息存储测试（既有容量/过期）与 257 个 Simulation 测试通过。
- 100/500/1000 混合基准修复前后数据见证据文件。

## 回滚

- 删除 `DeliverDueMessages` 的 `storageByCivilization` 缓存；
- 令 `crowdLod` 恒为 false（或移除 `DrawLod` 分支）。

世界/存档/哈希无需迁移。
