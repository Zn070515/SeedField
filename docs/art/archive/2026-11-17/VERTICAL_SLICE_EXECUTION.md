# SeedField 美术 Vertical Slice — 本轮执行计划

> 状态 `[PROPOSED]`。这是**正式美术管线的验证阶段**，不是新的游戏规则版本。建议在独立 `art/` 分支实施，并通过真实 Godot 截图与用户比选决定是否合并。

## 1. 本轮最终交付

一张可交互的**真正游戏场景**，不是网页/概念稿。画面中同时存在：

1. **种子核心**：不朽内核、五分支接口、受围困状态可辨。
2. **五分支设施**：至少能以轮廓辨认能源、感知、通信、状态、执行。
3. **模块化战构体**：一台战构体拥有武器/感知两种模块变化，图像与数值蓝图对应。
4. **地形**：可见地层、局部工业遗迹、导电网络、建造平台。
5. **真实反馈**：射击/命中、断电/恢复、消息发送/失联、设备残骸，事件必须来自现有 C# 状态。
6. **可控调试层**：默认玩家视图不显示无关范围圈；按键开启完整诊断覆盖层。
7. **基础 UI**：场景中选中单体显示名称、主要资源/部件/行动状态；工坊至少有一个与模型联动的大预览。

## 2. 优先实现顺序

### Gate 0 / 保存旧证据

- 固定审查 SHA，保存当前 `m0-combat`, `m0-workshop`, `m0-recovery` 截图作 before。
- 确认 `dotnet build SeedField.slnx`、`dotnet test SeedField.slnx`、Godot 截图命令是否可运行。
- 标准化素材目录、相机与渲染配置；不在这个阶段改动 SimulationCore。

### Gate 1 / 两套风格样片（先比选，不大量做）

以同一 3 件物体在两种相机方案中制作：种子核心、基础工体、能源接口设施。

- **A 斜俯视**与**B 严格俯视**，统一尺寸、光照、材质逻辑；每条路线至少 3 个视图（远/中/近）。
- 独立遮挡、比例与朝向测试；如可移动工体斜俯视必须多方向渲染，则记录单资产渲染耗时与内存成本。
- 用户选定一条路线前，不把任何方案记作 `[CONFIRMED]`。

### Gate 2 / 实体与世界替换

- 把工体 `DrawCircle` 正式替换成实体精灵/分层组件，不能损失实体状态显示。
- 用可拆分场景的设施替换圆点控制点；加入局部地形/管线和少量遗迹贴图。
- 核心区视觉与 `SeedCore` 相关状态绑定，不让美术代码直接修改它。
- 射程圈、通信圈、网格/ID/内部调试挪入 `TacticalOverlay` / `DebugOverlay`，默认关闭。
- 所有动画通过 `SimulationEvent` 或只读快照驱动。

### Gate 3 / 初版交互与信息层级

- 优先覆盖默认世界视图和选中设备信息；工坊增一个装配预览窗口。
- 避免直接重写现有五个功能面板；先提炼统一 Typography、Spacing、StatusToken 和 Panel 视觉规则。
- UI 缩放、对比度和焦点交互保持原有键盘操作。

### Gate 4 / 回归与验收

- 实机录制同一场景的 `normal`, `tactical`, `debug` 三种视图；至少两种镜头缩放。
- 建造、升级、失联、断电、胜负、残骸回收、核心复建各至少有一帧状态证据。
- Headless hash/仿真回归不能因视觉层变更而变化；如变化须停止并定位。
- 记录设备数量 `1 / 10 / 50 / 100` 时真实 FPS 和帧时，在**开发机**上的结果不可冒充最低配置表现。

## 3. 操作边界

- 不重构 `WorldSaveSerializer`、`SimulationEngine`、Jint 接口、离线对手包、安全隔离。
- 只读世界快照和公开事件；切勿把 `EntityState` 交给 VFX/节点写操作。
- 仍然保留旧 M0 调试画面开关作为诊断工具；不删除示例和自动测试。
- 不以截图数量、贴图数量、AI 生成图数量代替完成度。

## 4. 视觉验收标准（必须包含使用者视角）

| 检查项 | 满足条件 |
|---|---|
| 远景可读 | 不开 ID/范围圈也能区分核心、能源设施、战构体及 3 类用途 |
| 轮廓语言 | 灰度缩小图仍能区分功能，非纯阵营换色 |
| 工坊意义 | 改动模块后，游戏世界中设备的可见结构产生对应变化 |
| 状态因果 | 断电/失联/受损/射击来自真实状态，演出不假造结果 |
| 非调试体验 | 初看截图能判断这是一个具象游戏世界，不是仿真监视器 |
| 技术/商业 | 源资产可再生、授权明确、产出大小可控、无必需联网 |
| 质量回归 | 当前功能按键与基本游戏测试仍能运行，故障信息仍能找到 |

## 5. 评分与拒绝条件

用户与至少一名从未读源码的试玩者，在相同截图下分别评分：

- **实体与世界可信度** 30 分
- **三层缩放识别** 20 分
- **风格一致与材质控制** 20 分
- **状态反馈与交互可读** 20 分
- **生产成本可持续** 10 分

初步建议 Gate4 目标 >= 80/100 且无一项 <= 50% 满分；仅作为验收提议。下列情况**无论总分多高均退回**：

- 只有概念图没有实际游戏截图；
- 改变了仿真规则、隐瞒了未知敌人情报；
- 模块变化不可见；
- 不可溯源或许可证不清的素材；
- 需要开发者持续提供服务器/外部生成 API 才能运行。

## 6. 建议的代码拆分（名字仅供参考）

- `Presentation/WorldView` 负责地形、区域图层。
- `Presentation/EntityVisual` 负责机体/建筑的视觉状态与模块精灵。
- `Presentation/NetworkVisual` 负责能源/通信表现。
- `Presentation/CombatVfx` 负责武器、命中和损伤。
- `Presentation/TacticalOverlay` 负责射程、传感、线路提示。
- `Presentation/DebugOverlay` 负责当前 M0 诊断日志/测试标签。

不要一次造六个框架；只在有第二个复用点时抽象，逐步把 `Main.Draw.cs` 的设备/世界绘制搬走。

## 7. 回滚原则

每一个美术集成 PR 均可通过替换场景或可见性开关回退到 M0 渲染；**不能要求撤回已经验证的核心仿真功能**。
